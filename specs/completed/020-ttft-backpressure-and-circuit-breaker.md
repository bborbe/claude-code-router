## Summary

- The router already bounds how much cold prefill a provider starts at once (spec 019), but the ceiling is a fixed number an operator guesses once and never revisits — it does not shrink when the backend is visibly slowing down, and it does not stop sending when the backend is failing outright.
- This change adds two optional per-provider behaviours on top of that ceiling: a backpressure loop that halves the cold-prefill budget when the backend's own measured cold time-to-first-token rises (or when a request fails), and grows it back step by step while the backend is healthy; and a circuit breaker that stops sending entirely after repeated upstream failures, answering clients with a 429 they can back off from instead of a 5xx.
- Both are per provider and off by default: a provider with neither new knob set behaves exactly as it does today.
- Both are observable — the live budget is exported as a gauge, breaker state changes as a counter, and each change prints one INFO line naming the provider.
- The budget the backpressure loop shrinks is the cold-prefill ceiling spec 019 already ships; this change consumes it, it does not create it.

## Problem

The router's cold-start admission gate (spec 019) caps in-flight cold-prefill tokens at a fixed per-provider number. That number is chosen once, from a guess about the backend's throughput, and it stays put whether the backend is running at full speed or crawling. Observed live on 2026-10-10, a fleet burst drove a shared model host to serve nothing for about 17 minutes; the gates that exist bound concurrency and cold volume, but none of them reacts to the backend's own health. When the backend slows down, the router keeps admitting at the same rate and makes the queue worse; when the backend is failing every request, the router keeps forwarding every request and every client retry lands on a backend that is already down. The backend publishes no queue depth the router can read, so the router must use the one health signal it already measures itself — how long cold prefill takes to produce its first token — as the proxy, backing off when it rises and recovering when it settles, and it must stop sending when the backend is failing rather than feeding the failure.

## Goal

A provider the operator opts in becomes self-limiting against its backend's health. When the backend's own measured cold time-to-first-token rises above a configured threshold — or any request to it fails — the router shrinks the cold-prefill budget it admits against, halving it each unhealthy window and never below a floor, so a slowing backend is fed less work instead of more. While the backend is healthy the budget grows back in fixed steps toward the operator's configured ceiling. When the backend fails a configured number of requests in a row, the router stops sending: it answers clients with a 429 carrying a `Retry-After` for a short open period, then lets exactly one probe through — a healthy probe closes the breaker and normal service resumes, a failing probe reopens it. The router never answers a client with a 5xx of its own making. Both behaviours are per provider, off by default, observable as a live budget gauge and a breaker state-transition counter plus one INFO line per change, and reconfigurable by SIGHUP without a restart.

## Non-goals

- No change to the cold-prefill budget mechanism itself, the new-session start rate, the concurrency caps, or the 429 delay gate — those shipped (specs 011, 018, 019) and are consumed here unchanged.
- No per-upstream-host concurrency caps — shipped separately; this work does not touch them.
- No reading of a vLLM or any other backend's `/metrics`; the router's own measured cold TTFT is the health signal. No `llm-proxy` change.
- No removal or change of the cold-start gate's fixed burst behaviour — that is a sibling task's scope.
- No new Prometheus `status_class` value — a breaker 429 and a budget refusal both record through the existing `4xx_rate_limited` class; the two new series are additive.
- No persistent breaker state and no spill-to-disk — both behaviours are in-memory per provider and a reload resets them.
- No per-model or per-session budget or breaker — both are keyed per provider, like every existing gate.
- No operator-tunable 60s observation window, clean-recovery threshold, growth step, budget floor, breaker open period, or probe count — those are fixed internal constants with documented defaults.
- No scenario file — the behaviours are reachable by Ginkgo integration tests through the real dispatch path with an injected clock, so unit and integration tests in the implementation prompts suffice.

## Desired Behavior

1. TTFT backpressure, halving. Once per fixed 60 s window, a provider with `ttftBackpressureThresholdSeconds` enabled evaluates its window's median cold time-to-first-token and its failure count. If the median exceeds the configured threshold, or any upstream failure occurred in the window, the effective cold-prefill budget halves. A failure is a 5xx response from the upstream or from the router's own reverse proxy (which is how an upstream timeout surfaces — the proxy answers 502/504); a client-initiated disconnect is not a failure. At most one adjustment is applied per window, so a window that both rises and fails still halves once.
2. TTFT backpressure, recovery. After a clean window — median cold TTFT below the fixed 8 s threshold and no failure — the effective budget grows by the fixed 8192-token step, never above the configured ceiling (`coldPrefillBudgetTokens`). A window whose median sits between 8 s and the threshold, with no failure, holds the budget unchanged, so the loop does not oscillate around the threshold.
3. TTFT backpressure, floor. The effective budget never falls below a fixed floor of one sixteenth of the configured ceiling — one request's estimate at the budget's design concurrency — so a persistently unhealthy backend is fed less work but the gate never collapses to refusing every request.
4. Effective budget is live and per provider. The cold-start gate admits against the current effective budget rather than the value configured at construction, so a halving takes effect on the next cold request; each provider's effective budget and breaker are its own, so shrinking or stopping one provider never touches another, including two providers that share one upstream.
5. Circuit breaker, open. A provider with `breakerFailureThreshold` enabled counts consecutive upstream failures (5xx, timeouts included via the proxy's 5xx). A non-5xx response resets the count. When the count reaches the threshold the breaker opens: for a fixed open period of 30 s every request to that provider is answered HTTP 429 with the existing static Anthropic-shaped `rate_limit_error` body and an integer `Retry-After` header equal to the open period, and the upstream is not invoked. The router never answers with a 5xx of its own making.
6. Circuit breaker, half-open and close. When the open period elapses the breaker admits exactly one probe request while concurrent requests are answered 429. A probe whose response is not a failure closes the breaker and resets the consecutive-failure count, so normal service resumes immediately; a probe that fails reopens the breaker for a further open period.
7. Observability and configuration. Each effective-budget change emits one INFO line `[backpressure] provider=<name> budget=<n>` and each breaker state change emits one INFO line `[breaker] provider=<name> state=open|half-open|closed`. A new gauge `ccrouter_cold_prefill_budget_tokens{provider}` exports the live effective budget, and a new counter `ccrouter_breaker_state_transitions_total{provider,state}` counts transitions with its three `state` series pre-initialized to 0. Both behaviours are enabled by a per-provider leniently-validated knob (`ttftBackpressureThresholdSeconds`, `breakerFailureThreshold`), off when absent, 0, or negative, and a SIGHUP reload rebuilds the per-provider tree so changed values are live without a restart; a reload resets the in-memory budget and breaker state, which re-accumulate from the next requests.

## Constraints

- Config schema: `Provider` gains `ttftBackpressureThresholdSeconds int` (yaml `ttftBackpressureThresholdSeconds,omitempty`) and `breakerFailureThreshold int` (yaml `breakerFailureThreshold,omitempty`). Zero-value semantics must remain today's behaviour. Both are read at provider level only and are NOT copied onto `upstreams:` pool members — a knob on a member is silently ignored, mirroring the throttle and cold knobs documented under `docs/config.md`.
- Enabling rules: TTFT backpressure is enabled when `ttftBackpressureThresholdSeconds > 0`; it has an effect only when the cold-start gate is enabled (`coldPrefillBudgetTokens > 0`), because it adjusts that budget — with no cold budget configured the knob is inert. The circuit breaker is enabled when `breakerFailureThreshold > 0` and is independent of the cold gate.
- Fixed internal constants, documented as defaults and not exposed as knobs: the 60 s observation window, the 8 s clean-recovery median threshold, the 8192-token growth step, the budget floor divisor 16, the 30 s breaker open period, and the single probe per open→half-open transition. The two knobs' recommended starting values are 20 (seconds) and 5 (failures).
- The effective budget is the existing `coldPrefillBudgetTokens` value adjusted by the backpressure loop: it starts at the configured ceiling and moves between the floor (`coldPrefillBudgetTokens / 16`) and the ceiling. The cold-start gate must admit against the live effective budget, not a value frozen at construction; the cold gate's own lone-request admission guard, its queue, its rate check, and its release-on-first-content-delta behaviour are unchanged.
- The failure signal is the response status observed at the provider handler boundary: a 5xx counts, anything below 500 does not. An upstream timeout surfaces as the router's reverse proxy answering 502/504 and is therefore counted; a client disconnect is not a failure. The breaker and the budget loop observe the same status stream.
- The breaker's 429 reuses the existing `limiter429Body` constant and the existing `writeRateLimited` helper (`pkg/handler/concurrency-limiter.go`) — do NOT introduce a second 429 body or a second header-write path. The body is the same static generic message and must not carry provider name, upstream URL, queue depth, or breaker state.
- The median of a window with an even number of cold TTFT samples is the arithmetic mean of the two central samples. A window with no cold TTFT samples and no failure counts as clean (it grows); a window with a failure and no cold samples halves.
- Placement: the breaker wraps the provider handler outermost (outside the 429 delay gate and the cold-start gate) so an open breaker short-circuits the whole provider; the backpressure controller is constructed alongside the cold-start gate and adjusts that gate's effective budget. The model router's body read, alias resolution, `[1m]` strip, key routing, and system-lift flow are untouched.
- Logging uses `glog.V(n).Infof(...)` — no `fmt.Printf` / `println`. The two INFO lines are always-on (not behind a `-v` level), matching the `[throttle]` and `[coldgate]` lines.
- Errors go through `github.com/bborbe/errors`; no bare `return err`.
- Metrics: the `ccrouter_` prefix; the budget is a Gauge and the breaker transitions a Counter ending `_total`; the `state` label is bounded to `closed|open|half_open` and all three series are pre-initialized to 0 for an enabled provider; no high-cardinality label is added.
- Concurrency: shared state (the effective budget, the window samples, the consecutive-failure count, the breaker state) is mutated from concurrent request goroutines and must be safe under a mutex; no raw `go func()` — use `github.com/bborbe/run` for any background work.
- Time is taken from the router's injected clock (`github.com/bborbe/time`), never `time.Now()`, so windows, the open period, and the probe are testable without wall-clock sleeps; tests must not sleep through a real window.
- Adding a YAML field obliges an update to `docs/config.md` AND `docs/config.example.yaml`, plus a `CHANGELOG.md` entry under `## Unreleased`.
- Tests follow the repo's Ginkgo/Gomega convention with ≥80% coverage on new `pkg/<package>` code; `make precommit` is the gate. No new dependencies — the Go standard library plus the existing `bborbe/*` libraries suffice. No AI attribution.

## Security / Abuse

- The breaker and the budget loop react only to the upstream's own response status and the router's own measured cold TTFT — never to client-supplied values. A client cannot open the breaker or shrink the budget except by inducing genuine upstream failures, which is the intended response.
- The breaker's 429 body is the static `limiter429Body` constant and must not reveal the provider name, the upstream URL, the breaker state, or the failure count; the `Retry-After` value is the fixed open period and carries no internal detail. Upstream response bodies pass through unchanged.
- Bounded resources: the window's sample buffer is bounded by the number of cold requests in one 60 s window, the failure count is a single integer, the effective budget is bounded between the floor and the configured ceiling, and the breaker holds no per-request state — no unbounded growth, no unbounded goroutine accumulation.
- A client that disconnects while a request is in flight must not be counted as an upstream failure and must not hold breaker or budget state.
- Breaker and budget state are mutated from concurrent request goroutines; every read-modify-write must be under a mutex, and the tests must exercise concurrent requests.
- Config values are validated leniently and no new user input parsing, path handling, or credential handling is introduced.

## Do-Nothing Option

The router keeps feeding a slowing backend at a fixed rate and keeps forwarding every request to a backend that is failing, so the router amplifies both conditions instead of damping them: a slow backend gets a longer queue, and a down backend gets a retry storm on top of the failures. That is the condition behind the 2026-10-10 outage, and the mitigation shipped so far (spec 019) only caps cold volume at a number an operator picked once and never revisits. Cost of doing this: one backpressure controller, one breaker gate, two lenient per-provider knobs, two additive series, and the tests that cover them. Cost of not doing it: every future slowdown and every future backend failure is served at full rate until a human notices and edits the config.
